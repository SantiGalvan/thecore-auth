# Vincolare il logging di useEnvironmentInfo al config ed esportarlo pubblicamente

## Contesto
Follow-up dell'hook `useEnvironmentInfo` originale (#31), che aveva deliberatamente rimandato due
elementi a "una issue di follow-up": comportamento config-driven via `public/config.json` ed
export/documentazione pubblica. L'hook era stato agganciato temporaneamente in `src/App.jsx`
(`useEnvironmentInfo(); // TEMP: solo per validare i dati in console, vedi PR #32`) solo per
validare la forma dei dati loggati. L'utente ha chiesto di chiudere questo punto: legare le
chiamate `console.log` per singolo campo già esistenti a un flag di config che parte a `false` e
non rompe nulla se manca da `config.json`, esportare l'hook da `src/index.js` e rimuovere la
chiamata temporanea da `App.jsx`.

## Modifiche tecniche
```js
// logField e ogni funzione helper che lo chiama accettano ora `enabled` come
// primo argomento invece di leggere un flag a livello di modulo, perché questi
// helper vivono fuori dal corpo dell'hook e non possono chiamare useConfig()
// direttamente.
const logField = (enabled, name, value) => {
    if (enabled) console.log(`[useEnvironmentInfo] ${name}:`, value);
    return value;
};

const useEnvironmentInfo = () => {
    const { environmentInfoLog } = useConfig();
    const loggingEnabled = Boolean(environmentInfoLog);
    // destrutturare una chiave di config assente produce `undefined`, e
    // Boolean(undefined) === false — una chiave assente si comporta esattamente
    // come `false` senza bisogno di codice di guardia aggiuntivo.

    const staticInfo = useMemo(() => getStaticEnvironmentInfo(loggingEnabled), [loggingEnabled]);
    // ...ogni state/effect dei campi dinamici propaga loggingEnabled nello stesso modo
};
```

## Motivazione
`logField` e le funzioni helper che lo chiamano (`getStaticEnvironmentInfo`, `getLocaleInfo`,
`getOrientation`, `getConnectionSnapshot`, `readMediaQuery`, `useMediaQueryPreference`) sono
definite a livello di modulo, fuori dal corpo dell'hook, quindi non possono chiamare `useConfig()`
direttamente — il flag deve essere propagato come semplice argomento dall'unico punto che *può*
chiamarlo. Un flag mutabile a livello di modulo è stato considerato e scartato: avrebbe fatto
trapelare stato tra ogni istanza montata dell'hook e reso i test dipendenti dall'ordine di
esecuzione, mentre propagare un valore tramite argomenti mantiene ogni render puro e testabile in
modo indipendente. Affidarsi a `Boolean(environmentInfoLog)` invece di un controllo esplicito
`key in config` è stata una scelta deliberata: fa collassare automaticamente "chiave assente" e
"chiave impostata a `false`" sullo stesso percorso di codice, soddisfacendo il requisito "non
rompere nulla se non è in config.json" senza alcun ramo di codice dedicato. `useConfig()` lancia
un'eccezione se non c'è un `ConfigProvider` antenato, ma è un comportamento preesistente condiviso
da ogni altro hook/context di questa libreria che legge il config (es. `AuthProvider`) — chi
consuma questa libreria si aspetta già di avvolgere la propria app in `ConfigProvider`, quindi non
introduce alcun nuovo vincolo.
